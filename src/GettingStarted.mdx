# Sample Design System

A working design system built on [Base UI](https://base-ui.com) primitives, documented here in Storybook, with a token layer shaped to sync to Figma variables.

Forty-two components, four foundations pages, four full-screen patterns.

## Read it in this order

**Foundations** first. Colour, Typography, Space and shape, Motion. These are the decisions everything else inherits. Flip the theme toggle in the toolbar while you read: token names stay fixed, values change. That is the whole idea.

**Components** second. Each has a Default story, then a story per meaningful state, disabled included. Open the Controls panel and change props. Open the Accessibility panel and check it stays clean.

**Patterns** last. Four real screens assembled from the library: a settings page, a sign-up form, a data table and an application shell. This is where you find out whether the system holds together, because a component library can look immaculate in isolation and still be painful to build a page with.

## The two token layers

`src/tokens/primitives.css` holds raw material: colour ramps, the spacing scale, the type scale. The colour ramps are off-limits to components.

`src/tokens/semantic.css` holds roles: `--sds-color-accent`, `--sds-color-text-muted`, `--sds-color-danger-subtle`. Components use these and only these for colour. Theming means redefining that one file.

Why two layers? Because `--sds-brand-600` tells you what a colour *is*, and `--sds-color-accent` tells you what it is *for*. Only the second survives a rebrand, and only the second maps cleanly onto a Figma variable.

## What Base UI gives us, and what it does not

Base UI ships around 40 unstyled primitives: behaviour, keyboard handling and ARIA, with no opinion about appearance. Dialog, Select, Menu, Tabs, Tooltip and the rest come from there. We wrap them and style from tokens.

It deliberately ships nothing for Card, Badge, Alert, Table, Spinner or Breadcrumb, because those have no interaction logic worth abstracting. We wrote those ourselves. They are the easy ones.

The rule that follows: **if Base UI has a primitive, wrap it.** Never reimplement focus trapping, roving tabindex or `aria-expanded` by hand. That is where accessibility bugs come from, and it is the highest-value rule in `docs/conventions.md`.

## A worked example of why that rule exists

Every wrapper here was audited against Base UI's own reference implementations. That pass found six real bugs that typechecked perfectly and looked fine in a simple story:

- The Slider thumb had no keyboard focus ring, because the primitive puts focus on a visually hidden `input` inside the thumb, not on the thumb itself.
- Select's scroll container was on the wrong part, which silently disabled a documented public prop.
- Toasts beyond the queue limit stay mounted and marked `data-limited`, expecting CSS to hide them. Nothing did, so a fourth toast rendered as an undismissable card.
- Popups sized themselves with `100vw` instead of the `--available-width` the primitive publishes, so they could overflow near a viewport edge.

None of these were visible without comparing against the source. That is the difference between wrapping a primitive and wrapping it correctly.

## Branching

`docs/branching.md` has the model. Everything currently sits on `main`. When you start prototyping, branch from it; `design` exists as the long-lived branch for exploring in real code, and accepted prototypes come back through a normal feature branch rather than merging `design` directly.
